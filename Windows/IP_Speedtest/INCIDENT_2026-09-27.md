# Incident report: `eco-seo.cz/ip/` returned HTTP 404

## Executive summary

The IP and Speed Test service did not fail because of WordPress, Nginx, PHP, DNS, or the application code. The complete `eco-seo.cz` web root was restored on 2026-09-19 from a 2026-05-20 backup. The restoration script deleted every non-hidden item in the live web root before extracting that old archive. The `/ip/` microservice was deployed on 2026-09-03, so it could not exist in the May backup and was therefore not recreated.

The restoration script validated only the WordPress homepage. It did not inventory or verify non-WordPress applications living under the same web root. Consequently, the restoration was reported as successful while `/ip/` was already missing. A scheduled backup on 2026-09-20 then captured the degraded state without `/ip/`.

## Root cause

The direct technical cause was a destructive whole-web-root restore from a backup older than the independently deployed `/ip/` application.

The decisive restoration steps were:

1. Create a complete pre-restore files and database snapshot.
2. Delete `WEB_ROOT/*`.
3. Extract the selected historical site archive.
4. Restore the database.
5. Validate only the domain homepage.

Step 2 removed the microservice. Step 3 could not restore it because the selected archive was created before the microservice existed.

## Contributing factors

1. WordPress and a separate microservice shared one mutable web root without a restore manifest.
2. The restore procedure treated the historical site archive as the complete desired state, although GitHub contained newer independently deployed components.
3. The pre-restore snapshot was created correctly but was used only as rollback insurance; its non-WordPress top-level directories were not inventoried or merged back.
4. Post-restore validation checked only `/`, not every production endpoint.
5. There was no integrity guard or external health check dedicated to `/ip/`.
6. The next scheduled backup preserved the already degraded state, making later recovery from ordinary rolling backups less reliable.
7. Direct SSH and occasional HTTPS requests to RU-109 can time out during connection establishment; the deployment workflow therefore uses DE-222 as an SSH jump host and retries bounded public checks. This network condition did not cause the DE `/ip/` deletion, but it can otherwise produce misleading deployment failures.

## Resolution performed on 2026-09-27

1. Synchronized the local public Git repository with `origin/main`.
2. Located this canonical dual-domain project instead of copying files from another production server.
3. Installed `index.php` on DE-222 as `gincz:gincz`, file mode `0644`, with directory mode `0755`.
4. Verified PHP syntax and SHA-256 integrity. The deployed and canonical hash was `cf494b31f49ee1d7bc6bc5003856fce30cdf8391cdb4fcbaf1d4488b4529b7bb`.
5. Verified the public page, title, host-specific EU marker, ping API, geo lookup, 4 MiB download endpoint, upload endpoint, completion call, and cooldown.

## Permanent prevention

The project now includes a self-healing integrity guard:

- The canonical `index.php` is stored outside the WordPress web root at `/usr/local/share/gin-ip-speedtest/index.php`.
- A systemd timer runs every five minutes on both DE-222 and RU-109.
- The guard validates the protected source hash and PHP syntax.
- If `/ip/index.php` is missing or differs from the expected hash, the guard recreates it atomically with the correct owner and permissions.
- The guard verifies public HTTP 200, the page marker, and the ping API after every run.
- Results are written to the system journal under `gin-ip-speedtest-guard`.
- `deploy.ps1` installs the same canonical source and guard on both domains, preventing source drift.
- `test-guard.sh` performs a controlled missing-file simulation with automatic rollback protection and verifies the restored SHA-256 value.

## Mandatory restore checklist

Before restoring any website root:

1. List every top-level file and directory in the live web root.
2. List every top-level file and directory in the target archive.
3. Produce and review the difference. Treat live-only paths as separate applications until proven otherwise.
4. Preserve a complete pre-restore files and database snapshot.
5. Restore the historical WordPress state.
6. Reconcile live-only applications from their canonical repositories or the pre-restore snapshot.
7. Run the endpoint manifest, not only a homepage probe.
8. Confirm the protected integrity guards and timers are active.
9. Only then declare the restoration complete and allow the next rotating backup to become the new baseline.

For this project, the required endpoint manifest is:

- `/ip/` -> HTTP 200 and title marker `IP & Speed Test`
- `/ip/?action=ping` -> JSON containing `"status":"ok"`
- `/ip/?action=geo` -> valid JSON with resolved location data when upstream providers are available
- `/ip/?action=download` -> HTTP 200 and 4,194,304 bytes
- `/ip/?action=upload` -> JSON confirming the received payload size
- `/ip/?action=complete` and `/ip/?action=check_cooldown` -> 20-second cooldown state

## Known evidence boundary

The evidence proves that the service existed in the pre-restore archive, that the restoration script deleted the complete web-root contents, that the selected historical archive predates and omits the service, and that the first post-restore backup also omits it. No separate later deletion event is needed to explain the incident. The exact process invocation record is not present in interactive shell history, so the execution time is bounded by the pre-restore artifact and subsequent filesystem state rather than a shell-history timestamp.
